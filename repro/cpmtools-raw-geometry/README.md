# cpmtools 2.23 raw-image geometry reproduction

cpmcp built against libdsk 1.4.2 can silently extract incorrect bytes from
raw CP/M images even with an explicit disk definition and `-T raw`.
The same cpmtools 2.23 source built with POSIX I/O extracts correctly.
The proposed patch below also makes the libdsk build extract correctly.

This reproduction uses generated sector counters and CP/M directory entries.
It requires no emulator, operating-system image, or software collection.
All image contents can be regenerated by `generate.py`.

The tested environment was macOS on Apple Silicon, cpmtools 2.23, and
libdsk 1.4.2. Homebrew's installed cpmcp and an independently built unmodified
cpmtools 2.23/libdsk executable both reproduced the failure. The source-built
POSIX and patched libdsk executables passed all three fixtures.

| Image | Raw size | Unpatched libdsk | POSIX | Patched libdsk |
| --- | --- | --- | --- | --- |
| four-mb-failing.dsk | 4,177,920 bytes | Wrong data, successful exit | Exact match | Exact match |
| four-mb-control.dsk | 4,177,920 bytes | Exact match | Exact match | Exact match |
| large-failing.dsk | 536,870,912 bytes | Wrong data, successful exit | Exact match | Exact match |

Each image contains `1:PATTERN.BIN`, which is exactly 16,384 bytes long.
The large image puts the file beyond the first two 2 MiB logical tracks.
This exercises the mapping error that small files near the beginning of P:
can miss. The 512 MiB image is sparse after its first 12 MiB when generated.
Unpacking the supplied ZIP can allocate the full image sizes.

The 4 MB failing and control images differ in exactly one byte. The first
CP/M directory entry is `0:VOLUME.TXT` in the failing image and
`0:TOLUME.TXT` in the control. PATTERN.BIN, its allocation, and all data
sectors are identical. Neither filename should affect extraction of another
file.

Reproduce using the supplied fixtures and the installed libdsk-backed cpmcp.
Run from the directory containing this README.

```sh
cd fixtures
cpmcp -T raw -f z80pack-hd four-mb-failing.dsk 1:PATTERN.BIN actual-4mb.bin
cmp four-mb-failing.expected.bin actual-4mb.bin

cpmcp -T raw -f z80pack-hd four-mb-control.dsk 1:PATTERN.BIN actual-control.bin
cmp four-mb-control.expected.bin actual-control.bin

cpmcp -T raw -f z80pack-hdb large-failing.dsk 1:PATTERN.BIN actual-large.bin
cmp large-failing.expected.bin actual-large.bin
```

The first and third cmp commands report differences and return 1. The control
cmp returns 0. Each cpmcp command itself returns 0. The cpmcp output filenames
must be unused, so remove extracted output files before repeating the commands.
The included diskdefs contains the supplied z80pack-hd and z80pack-hdb
parameters without changes.

The counter at the beginning of each 128-byte sector identifies its physical
sector number in the raw file. The failing results were as follows.

| Image | Expected first sector | Extracted first sector |
| --- | --- | --- |
| four-mb-failing.dsk | 272 | 528 |
| four-mb-control.dsk | 272 | 272 |
| large-failing.dsk | 32896 | 65664 |

The exact code path is identifiable in the release sources.

1. In cpmtools 2.23 `device_libdsk.c`, `Device_open()` calls `dsk_getgeom()`
   at line 66 when no explicit libdsk format suffix is supplied. Selecting
   `-T raw` still enters that path.
2. In libdsk 1.4.2 `lib/dskgeom.c`, `dg_pcwgeom()` starts at line 503.
   It accepts a first byte of 0 or 3 and interprets `bootsec[1] & 3` at
   lines 521–525. A CP/M directory entry in user 0 starts with 0. The next
   byte is the first filename character. ASCII V is 0x56, whose low two bits
   are 2. Case 2 sets `dg_sidedness = SIDES_OUTBACK`. ASCII T is 0x54 and
   selects case 0, `SIDES_ALT`.
3. Back in cpmtools `Device_setGeometry()`, lines 88–89 replace the sector
   size and sectors per track from diskdefs. Lines 90–103 retain or replace
   cylinder/head counts. The inferred `dg_sidedness` survives.
4. `Device_readSector()` passes logical sectors to `dsk_lread()`.
   libdsk's `lib/dskread.c` calls `dg_ls2ps()`, whose conversion is in
   `lib/dsklphys.c`. The retained side ordering changes physical track
   selection. The raw driver consequently returns bytes from another offset.

A small optional diagnostic exposes the probe directly.

```sh
libdsk_prefix=$(brew --prefix libdsk)
cc probe_geometry.c -I"$libdsk_prefix/include" -L"$libdsk_prefix/lib" \
  -ldsk -o probe_geometry
./probe_geometry fixtures/four-mb-failing.dsk
./probe_geometry fixtures/four-mb-control.dsk
```

With libdsk 1.4.2 the first command reports sides=1, cylinders=79, heads=2,
sectors=76, and sector_bytes=268435456. The control reports sides=0 and
heads=1. Those values are inferred from directory filename bytes.

`raw-linear-order.patch` is a proposed cpmtools integration fix. In
`Device_open()`, it skips boot-sector inference for the raw driver when
no explicit libdsk format was supplied, initializes linear ordering and
sector base 1, and lets `Device_setGeometry()` supply the diskdef geometry.
The existing explicit `-T raw,FORMAT` path and diskdefs `libdsk:format` path
retain their format selection. This patch is a tested candidate for maintainer
review. Compatibility with other raw layouts and the wider libdsk driver
set still needs upstream assessment.

Build the comparison executables from the same upstream source tarball.
The following commands assume macOS, make, a C compiler, Homebrew libdsk,
and Python 3. Use another libdsk prefix as appropriate on other systems.

```sh
mkdir -p source posix libdsk patched bin
curl -L --fail https://www.moria.de/~michael/cpmtools/files/cpmtools-2.23.tar.gz \
  -o source/cpmtools-2.23.tar.gz
printf '%s  %s\n' \
  7839b19ac15ba554e1a1fc1dbe898f62cf2fd4db3dcdc126515facc6b929746f \
  source/cpmtools-2.23.tar.gz | shasum -a 256 -c -
tar -xzf source/cpmtools-2.23.tar.gz -C posix --strip-components=1
tar -xzf source/cpmtools-2.23.tar.gz -C libdsk --strip-components=1
tar -xzf source/cpmtools-2.23.tar.gz -C patched --strip-components=1
libdsk_prefix=$(brew --prefix libdsk)
(
  cd posix
  ./configure
  make cpmcp
)
cp posix/cpmcp bin/cpmcp-posix
(
  cd libdsk
  ./configure --with-libdsk="$libdsk_prefix"
  make cpmcp
)
cp libdsk/cpmcp bin/cpmcp-libdsk
(
  cd patched
  patch -p1 < ../raw-linear-order.patch
  ./configure --with-libdsk="$libdsk_prefix"
  make cpmcp
)
cp patched/cpmcp bin/cpmcp-patched
python3 check.py fixtures --posix bin/cpmcp-posix \
  --libdsk bin/cpmcp-libdsk --patched bin/cpmcp-patched
```

cpmtools 2.23 selects POSIX I/O when no libdsk option is supplied. Its
configure script treats `--without-libdsk` as a path named "no", so use
plain `./configure` for the POSIX comparison. Stock POSIX builds reject
`-T raw`, so `check.py` omits that option for the POSIX executable.

The checker verifies the expected failure pattern and requires the patched
and POSIX builds to return exact bytes for every fixture. Its captured
results are in `results.txt`. The proposed patch also passed extraction of
the original 324,352-byte guest-created I: file.

To regenerate the fixtures into an unused directory, run the generator.

```sh
python3 generate.py regenerated-fixtures
```

`cases.json` records the expected outcomes, file sizes, and payload hashes.
`SHA256SUMS` covers every generated fixture and metadata file. Generation
refuses to overwrite existing images.

- [libdsk 1.4.2 source](https://www.seasip.info/Unix/LibDsk/libdsk-1.4.2.tar.gz), SHA-256 `71eda9d0e33ab580cea1bb507467877d33d887cea6ec042b8d969004db89901a`.

These results establish the affected integration path for the tested versions.
They do not establish behavior in later upstream releases. No report has been
submitted to either maintainer as part of preparing this bundle.
